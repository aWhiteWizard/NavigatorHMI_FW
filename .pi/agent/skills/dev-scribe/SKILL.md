# 开发书记员（Documentation Scribe）

**核心规程：所有文档起草由书记员完成，主代理每稿必审后方可定稿。**

## 成本优化铁则（主代理禁区）

| 任务 | 永远不要自己做 | 交给谁 |
|------|---------------|--------|
| 读 >100行日志 | ❌ | 📊 log-analyst (v4-pro) |
| 读 >100行文档 | ❌ | 📊 log-analyst (v4-pro) |
| 起草文档/commit | ❌ | 📜 scribe (v4-flash) |
| 看原理图/PCB | ❌ | 🔍 diagram-reader (kimi-k3) |

主代理只做三件事：**写简报**（给足事实）+ **审查子代理产出** + **写代码/执行命令**。

## 分工铁律

| 环节 | 谁做 | 说明 |
|------|------|------|
| **起草** | 书记员（DeepSeek） | 所有文档初稿：指南、README、变更记录、迁移文档、**含 skill 文件初稿** |
| **审查** | 主代理（Kimi） | 每份初稿必审，无例外 |
| **定稿/小修订** | 主代理 | 审查通过后定稿；几个字的小修订直接改，不起草 |
| **简报** | 主代理 | 给书记员的任务简报，事实必须给全 |

## 工作流程（五步走）

1. **主代理写简报**（事实清单给全，见下方模板）
2. **播报一行**：`📜 调用书记员（deepseek-v4-flash）：去起草 <文件>（一句话内容）`
3. **书记员起草**：`pi -p --provider deepseek --model deepseek-v4-flash "<简报>"`，直接写入目标文件
4. **主代理审查**（见下方审查机制）
5. **定稿或打回**

## 审查机制（每稿必审，无一例外）

**审查是不可跳过的固定环节。** 无论文档多短（哪怕只加一段），无论改动多小（哪怕只改一行），Leader 都必须执行审查。不存在"太简单不用审"。

主代理收到初稿后逐项检查：

1. **事实核对** —— 对照简报事实清单，查编造、走样、遗漏（最重要）
2. **结构检查** —— 章节完整、逻辑通顺
3. **风格检查** —— 中文、与项目文档风格一致（表格、代码块、标题分级）

**审查深度分级**：
- 普通文档（README/指南/记录）：抽查关键节 + 事实核对
- skill/行为指令类文件：**逐节严审**（写歪了污染以后所有会话）

**审查结论处理**：
- ✅ 通过 → 定稿，向用户汇报"书记员起草，已审查定稿"
- 🔧 小错（个别事实偏差、格式问题）→ 主代理直接 edit 修掉，不打回
- ❌ 大错/方向偏 → 打回：把具体问题列给书记员，重写对应章节

## 任务简报模板（质量关键）

书记员是**独立会话，没有本次对话上下文**。简报必须包含：

0. **非交互指令**（必加，否则它可能只提问不干活）：「这是一次性非交互任务，禁止提问，必须使用 write 工具实际创建目标文件」
1. **任务**：写/更新哪份文档，目标读者
2. **事实清单**：准确的文件名、命令、参数、版本、决策——**绝不让它猜事实**
3. **参考**：让它 read 的相关文件路径（学风格/查细节）
4. **风格**：中文、结构要求
5. **输出**：直接写到目标文件（主代理不搬运内容，省 token）

## 适用与不适用

**适用**：所有文档起草（含 skill 文件初稿、git commit 信息）
**不适用**：
- 小修订（几个字/几行）→ 主代理直接改
- 日志根因分析 → 走 log-analyst（推理模型）
- 代码编写/修改 → 主代理（书记员不写代码）

## 成本控制

- 书记员读文件、写文档按 DeepSeek 价格计（约为主模型 1/10~1/30）
- 主代理消耗：简报（几百 token）+ 审查（普通文档抽查，skill 严审）
- 书记员输出直接写文件，不进主代理上下文（避免双重计费）
