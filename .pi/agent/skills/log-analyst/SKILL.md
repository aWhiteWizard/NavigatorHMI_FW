# 日志分析员（Log Analyst / Doc Retriever）

主代理负责修复和决策，日志/文档的阅读和初步诊断委派给低成本推理子代理。

**一个代理，两类输入**：日志找错 + 文档找章节，本质都是"读大文本→提取关键信息→结构化输出"。

## 首要原则：大文本不贴对话

贴进对话的每一行日志/文档都按主模型价格计费。**永远先落文件**再走此流程。

## 调用方式

**调用前先向用户播报一行**：

> 📋 调用日志分析员（deepseek-v4-pro）：分析 `logs/xxx.log`（构建失败根因）
> 或
> 📖 调用日志分析员（deepseek-v4-pro）：从 `文档.txt` 中检索 `<主题>`

## 适用与不适用

**适用**：大日志（几百 KB+）根因分析、报错位置不明、多层嵌套错误、warnings 统计归类
**同时适用**：大文档（>500 行）关键章节/主题抽取
**不适用**：grep 能定位的简单错误、<100 行日志（主代理直接读）、文档撰写成文（走 dev-scribe）

## 分析任务简报模板

### 日志分析
1. **日志路径** + 背景（在编译什么、什么工具链、期望什么）
2. **导航提示**："先用 grep 定位 Error/FAILED，再 read 偏移量读上下文，不要一次全读"
3. **输出契约**：根因（一两句）+ 关键证据（报错原文 10~30 行）+ 修复建议

### 文档检索
1. **文档路径** + 项目背景 + 检索主题/关键词
2. **导航提示**："先用 grep 定位关键词，再 read 偏移量读上下文"
3. **输出契约**：按主题分节，每节含章节位置 + 关键参数原文 + 与项目关联

## 与其他子代理的分工

- **找错/根因 + 文档检索** → 本代理（推理模型）
- **成文/摘要写文档** → 书记员 dev-scribe（chat 模型）
- 同一日志既要分析又要写成文档：先本代理出诊断，主代理把结论喂给书记员成文
